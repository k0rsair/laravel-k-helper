# Bound container navigation still fell through to interfaces

**Date:** 2026-05-26 23:06
**Files:** src/providers/documentLinkProvider.ts, src/providers/boundDefinitionLinks.ts, src/providers/boundDefinitionResolver.ts, src/indexer/scanners.ts, src/extension.ts, test/unit/boundDefinitionLinks.test.ts, test/unit/boundDefinitionResolver.test.ts, test/unit/scanners.test.ts
**Severity:** high

## Problem

Bound Laravel container calls such as `app(Contract::class)->method()` and constructor-injected contract properties still navigated to the interface/contract instead of the bound concrete implementation.

## Root Cause

The original fix relied on a standard VS Code definition provider. In real editor usage, generic PHP language-server navigation can still handle the same symbol and send the user to the interface. The scanner also only handled class-to-class bindings and skipped simple provider factories such as `fn () => new Service()` and closure factories returning `new Service()`.

## Solution

Added a document-link provider for bound container calls so Cmd/Ctrl-click over supported contract calls has an explicit concrete target. Extended container binding scanning to detect arrow and closure factories that return a concrete class. Added resolver and link tests covering direct `app(...)` calls, constructor-injected properties, alias names, and factory-style provider bindings.

## Prevention

Tests for editor navigation features must cover the user-visible provider/link layer, not only the low-level parser. Container binding support should include common Laravel provider styles before declaring the navigation path complete.
